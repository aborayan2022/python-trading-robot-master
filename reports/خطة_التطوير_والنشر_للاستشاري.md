## 2. Deployment Plan (خطة النشر — ثلاث مراحل إجبارية)

### المرحلة 1: Replay (تأكيد سلامة التشغيل)
**الهدف:** إثبات أن الحلقة + الاستراتيجية + الحوكمة تعمل بلا إنترنت ولا أوراق اعتماد.

```bash
export PYROBOT_PROFILE="replay"
export PYROBOT_SIGNAL_SOURCE="example"
python -m pyrobot.runtime.loop
```

**معايير النجاح:** LAUNCH إلى RUN دون أخطاء، أشرطة تتوالى، لا مخالفة لمحرك المخاطر.

### المرحلة 2: Alpaca Paper (فترة القبول — 3 إلى 6 أشهر غير متقطعة)
**الوجهة الوحيدة المعتمدة قبل أي مال حقيقي.** يبقى التداول الحقيقي مقفلاً حتى تنتهي هذه الفترة.

```bash
export ALPACA_API_KEY="..."
export ALPACA_SECRET_KEY="..."
export PYROBOT_PROFILE="alpaca_paper"
export PYROBOT_SYMBOLS="MSFT,AAPL"
export PYROBOT_BAR_INTERVAL="60"
python -m pyrobot.runtime.loop
```

**التشغيل المسبق (smoke، أداة جاهزة منذ 6 سبتمبر):**
```bash
python us_strategy_paper_smoke.py
```
- بدون واجهات برمجية للوسيط → خروج 2 `missing_dependency`.
- بدون مفاتيح Alpaca → خروج 0 `missing_credentials` (تخطٍّ آمن، لا أخطاء).
- جلسة السوق الأمريكي مغلقة → خروج 0 `market_closed` (لا يضرب الـ API إطلاقًا).
- في جلسة مفتوحة وبمفاتيح صحيحة → يبني الأنبوب الإنتاجي (`build_alpaca_pipeline` + `alpaca_polling_provider` + `USTrendFollowStrategy` + `RuntimeMetrics`) ويعمل بعدد أشرطة محدد (افتراضي 30 بار × 3 ثوان) ويكتب تقريرًا في `data/reports/us_strategy_paper_smoke_<timestamp>.json`.

**معايير نجاح فترة القبول (من runbook):**
1. تسوية ثابتة (position/cash/orders) بلا أي Mismatch.
2. سلامة سلسلة التدقيق في كل جلسة (`verify_file_integrity()`).
3. سحوبات تحت السيطرة (خارج حدود 10%).
4. أداء النموذج Out-of-Sample بعد التكاليف كما موثق في بوابات القبول.

**المراجعة اليومية المطلوبة:** `data/audit/ledger.jsonl` + `data/metrics/runtime_metrics.jsonl` + تقرير `pyrobot.monitoring.build_daily_report` + نشاط حساب Alpaca الورقي.

### المرحلة 3: Alpaca Live (البوابة النهائية)
- **لا تُفعَّل إلا بعد 3–6 أشهر ورقي سليمة تمامًا** وموافقة كتابية من مالك المشروع.
- تُفعَّل حصريًا عبر `PYROBOT_ALLOW_LIVE_TRADING=true` مع مبالغ صغيرة كمرحلة أولى.
- القواعد الحابسة تبقى مفعّلة: رفض BUY لرموز القطاع UNKNOWN عند 25% من المحفظة، حد 500 أمر مفتوح، قاطع خسارة 10% (إيقاف فوري).

### أوامر التوقف الحتمية (Stop Conditions)
يجب أن يتوقف النظام فورًا عند أي مما يلي: بيانات مفقودة/قديمة في الـ polling، عدم تطابق في التسوية، اختراق حد خسارة/سحب/تعرض، كسر سلامة سلسلة التدقيق، أو أعطال وسيط متكررة.

## 3. Development Plan (خطة التطوير — حسب الأولوية)

| # | البند | السبب | التقدير |
|---|---|---|---|
| 1 | إعادة جدولة تدريب تلقائية (أسبوعية) على نفس واجهة الحوكمة | التعلّم الدوري سؤال المدير العام الوحيد المفتوح؛ لا جدولة ذاتية اليوم | 2–3 أيام |
| 2 | ترحيل التخزين من ملفات إلى قاعدة بيانات (PostgreSQL جاهز في compose) | الملفات تكفي للتشغيل المحدود فقط وتصبح عائقًا عند التوسع | 3–5 أيام |
| 3 | مراجعة تعريف الهدف التنبؤي (`dir_5`) وآفاق زمنية/أهداف عائد معدل بالمخاطر بديلة | ثلاث نماذج فشلت في تجاوز الشراء والاحتفاظ؛ المشكلة قد تكون في تعريف الهدف لا النموذج | 3–5 أيام |
| 4 | إضافة مساعد LLM استشاري داخل طبقة `pyrobot/ai/context.py` فقط | نقطة الربط جاهزة؛ يُقيَّد حصريًا بالتفسير والاقتراح، لا تنفيذ ولا تجاوز لمحرك المخاطر | 3–5 أيام |
| 5 | دعم فئات أصول/أسواق إضافية (بالأولوية: عملات رقمية عبر Alpaca) | قناة الوسيط جاهزة؛ يتطلب منطق جلسة سوق مرن + دقة عشرية | 5–8 أيام |
| 6 | توسعة `USTrendFollowStrategy` بمتغيرات مُمتحنة (أفق شرائح مختلف، فلتر زخم إضافي) خلف نفس الحوكمة | البيوجديج المحلي أصبح جاهزًا وأظهر 91.91% صافية؛ التوسيع يجب أن يمر ببوابة القبول نفسها | 2–4 أيام |

**قاعدة صارمة لكل بند تطوير:** أي نموذج أو استراتيجية أو إشارة جديدة تمر إجباريًا عبر بوابة المنفعة الاقتصادية بعد التكاليف ولا تُفعَّل على الورق إلا بعد موافقة الحوكمة — وهو نفس المبدأ الذي رفض حتى الآن ثلاث ترقيات للنماذج.

## 4. Exit Criteria (شروط إنهاء عقد الاستشاري أو التحوّل للتشغيل الذاتي)

1. 3–6 أشهر ورقي متصلة بلا انتهاك لبنود stop conditions.
2. نموذج/استراتيجية واحدة على الأقل تتفوق على الشراء والاحتفاظ بعد التكاليف لخارج العينة.
3. توثيق تشغيلي كامل (runbook + خطة DR + سجل تدقيق سليم).
4. انتقال المعرفة: الفريق يستطيع تشغيل الدورات وإعادة التدريب والتقييم ذاتيًا.
